Getting started

tddlog is an exact inference engine for probabilistic Datalog. It reads a probabilistic logic program written in ProbLog, or a Bayesian or Markov network, and prints the probability of each of its queries given its evidence; translators reduce Dice programs and LPADs to ProbLog (below). The answers are exact: tddlog grounds the program to probabilistic Datalog, compiles it into tree decision diagrams and counts the queries on them.

There are three ways to run it:

  • In the browser: the playground runs tddlog in the tab, built for WebAssembly. Nothing is installed.
  • On the command line: Cargo builds tddlog from the repository and installs it in its bin directory ($HOME/.cargo/bin): 
    cargo install --locked --git https://github.com/Tractables/tddlog tddlog
    The build needs Rust 1.88 or newer and a C++ compiler (gcc 12 or newer, or a recent clang) for the tree-decomposition solver that the goatd library vendors. --locked builds with the versions of the dependencies that the repository's tests ran with. In a checkout of the repository, cargo build --release builds the same program as target/release/tddlog.
  • From Python: build the package from a checkout, as the Python page shows, then tddlog.solve(program) (below).

The commands below run in a checkout of the repository (git clone https://github.com/Tractables/tddlog), whose examples/ holds the programs they read.

A first program

examples/alarm.pl is the alarm example of Fierens et al. (2015):

0.1::burglary.
0.2::earthquake.
0.7::hears_alarm(john).
0.4::hears_alarm(mary).
alarm :- burglary.
alarm :- earthquake.
calls(X) :- alarm, hears_alarm(X).
evidence(calls(john), true).
query(burglary).
query(earthquake).
query(calls(mary)).

Each line p::fact. is a probabilistic fact, true with probability p independently of the others. A choice of truth values for the four facts is a possible world, and in each world the rules decide which other atoms hold: the alarm goes off if there is a burglary or an earthquake, and a person calls if the alarm goes off and they hear it. The evidence keeps the worlds in which John calls, and each query asks for the probability of an atom over those worlds.

$ tddlog examples/alarm.pl
burglary:       0.357143
earthquake:     0.714286
calls(mary):    0.400000

The answers can be checked by hand. The alarm goes off with probability 1 − 0.9 × 0.8 = 0.28, so John calls with probability 0.28 × 0.7 = 0.196. A burglary sets the alarm off, so a burglary and John's call happen together with probability 0.1 × 0.7 = 0.07, and P(burglary | John calls) = 0.07 / 0.196 = 0.357143. Once John calls, the alarm has gone off, and Mary hears it with probability 0.4.

--evidence-probability adds a line with P(e), the probability of the evidence, in scientific notation and as its base-10 logarithm, which stays exact where P(e) is smaller than the least floating-point number:

$ tddlog --evidence-probability examples/alarm.pl
burglary:       0.357143
earthquake:     0.714286
calls(mary):    0.400000
P(e):   1.960000e-1     log10 -0.707744

Open this program in the playground, where it can be edited and run again.

The language

tddlog reads ProbLog without cut: atoms whose arguments are constants, numbers, variables and compound terms, lists among them. A program for tddlog is a program ProbLog reads too, and the repository's tests check tddlog's answers against ProbLog's.

Facts and rules

edge(1,2).                           % a fact
0.6::edge(2,3).                      % a probabilistic fact
path(X,Y) :- edge(X,Y).              % rules
path(X,Y) :- edge(X,Z), path(Z,Y).
0.7::alarm :- burglary.              % a probabilistic rule

A name that starts with a lower-case letter is a constant or a predicate, one that starts with an upper-case letter or _ is a variable, and % starts a comment, as does /*. A probability is a number or a fraction, such as 1/3::a. A probabilistic rule makes one independent choice for each instance of its variables: under 0.6::q(X) :- p(X)., each q(X) whose p(X) holds is true with probability 0.6, independently of the others. A body is a conjunction (,) and may hold disjunctions (;) in parentheses.

Annotated disjunctions

0.2::color(red); 0.5::color(green); 0.3::color(blue).
0.05::tub(yes); 0.95::tub(no) :- asia(yes).

An annotated disjunction makes one choice among its heads: here the color is red with probability 0.2, green with 0.5 and blue with 0.3. Probabilities that sum to less than one leave the rest of the mass to none of the heads. With a body, as on the second line, the choice is made where the body holds, once for each instance of the variables; a table of a Bayesian network is one annotated disjunction per row.

Negation

b :- \+ a.
c :- not(a).
\+ d :- b.

\+ a, or not(a), holds in a world where a cannot be derived: negation as failure. A negated literal may reach back into its rule's own recursion, as in the game and the gear wheels below. tddlog then reads each world by its well-founded model, which is ProbLog's semantics, and answers where that model is two-valued in every world; where some world leaves an atom undefined the program has no distribution, and tddlog says so rather than answer. A negated head, as on the third line, makes d false wherever b holds, as in ProbLog.

Arithmetic and comparisons

n(1). n(2). n(3).
0.5::x(N) :- n(N).
s(S) :- x(A), x(B), A < B, S is A + B.

is evaluates arithmetic as ProbLog does, which is as Python does: +, -, *, / (in floating point: X is 4 / 2 binds 2.0), // (rounded down), mod, **, abs, min, max and the like. The arithmetic comparisons <, >, =<, >=, =:= and =\= evaluate both sides; = and \= unify terms, and ==, \==, @< and the like compare them in ProbLog's standard order. tddlog grounds a program before it compiles it, so the variables of an arithmetic expression or a comparison must be bound by a positive atom of the body; tddlog orders a body so that the atoms that bind come first.

Terms, lists and findall

0.4::item(a). 0.7::item(b). 0.5::item(c).
cost(a, 3). cost(b, 4). cost(c, 5).
first_two :- nth1(1, [a, b, c], X), nth1(2, [a, b, c], Y), item(X), item(Y).
total(S) :- findall(C, cost(_, C), L), sum_list(L, S).
query(first_two).
query(total(_)).

Arguments may be compound terms, f(X, g(Y)), and lists, [a, b | T]; N1 = N - 1 binds N1 to the term N - 1, which is evaluates. The list predicates of ProbLog's library are built in: member/2, memberchk/2, append/3, length/2, nth0/3, nth1/3, last/2, reverse/2, sum_list/2, max_list/2, min_list/2, sort/2 and between/3, unless the program defines its own. findall/3 collects the solutions of a deterministic goal in ProbLog's order, and its list may then be counted, summed or sorted under probabilistic facts, as total above. tddlog grounds the program to one without terms, which it compiles as any other: a term is a value of the grounding.

Evidence and queries

evidence(calls(john), true).
evidence(calls(mary), false).
evidence(alarm).                     % the same as evidence(alarm, true)
query(burglary).
query(\+ burglary).
query(path(1,X)).                    % each path(1,X) that can hold

Evidence is a list of observations, each an atom and its value; the queries are answered given all of them. A query with variables asks for each of its instances that can hold in some world, and a rule whose head is a query, as query(path(1,X)) :- target(X)., for the instances its body allows. Evidence that no world satisfies is reported as evidence is inconsistent: probability zero.

What tddlog does not read

  • strings, cut, if-then-else and the built-ins beyond arithmetic, comparison, the list predicates and findall/3;
  • a query, an observation or a call of a predicate that has no clauses, which ProbLog refuses too: a misspelt name stops tddlog rather than read as false, though a call that no query and no observation reaches is left alone;
  • a findall/3 over a probabilistic goal, whose answer in ProbLog is a distribution over lists, over a recursive goal, or with a solution that has two proofs, which ProbLog lists twice;
  • a grounding that does not end, as nat(s(X)) :- nat(X). asked for every nat(X);
  • facts with variables (p(X).) and rules that are not range restricted: each variable of a head, of a negated literal and of a comparison must occur in a positive atom of the body, though a query or a call can bind a head's variables, and a variable that only a negated atom has is read as ProbLog reads it (\+ p(X, _): no p(X, Y) for any Y).

Each of these stops tddlog with a message and exit status 1, as in

$ tddlog choice.pl
parse error: line 1: if-then-else is not supported

Of ProbLog 2.3's 109 system tests, tddlog passes 52, reports as errors the 9 that ProbLog expects to fail, and reports the other 48 as unsupported (tests/problog_suite.py).

Worked examples

Each program is in the repository's examples/, and tests/it/examples.rs checks its answers under several vtree strategies.

A Bayesian network with evidence

examples/bn_asia_evidence.pl is the asia network of Lauritzen and Spiegelhalter (1988), which relates a visit to Asia, smoking, tuberculosis, lung cancer and bronchitis to an x-ray and to dyspnoea. Each variable's table is one annotated disjunction per row of its parents' values; either, which holds where the patient has tuberculosis or lung cancer, is a deterministic node, written as rules:

0.01::asia(yes); 0.99::asia(no).
0.05::tub(yes); 0.95::tub(no) :- asia(yes).
0.01::tub(yes); 0.99::tub(no) :- asia(no).
0.5::smoke(yes); 0.5::smoke(no).
0.1::lung(yes); 0.9::lung(no) :- smoke(yes).
0.01::lung(yes); 0.99::lung(no) :- smoke(no).
0.6::bronc(yes); 0.4::bronc(no) :- smoke(yes).
0.3::bronc(yes); 0.7::bronc(no) :- smoke(no).
either(yes) :- lung(yes), tub(yes).
either(yes) :- lung(yes), tub(no).
either(yes) :- lung(no), tub(yes).
either(no) :- lung(no), tub(no).
0.98::xray(yes); 0.02::xray(no) :- either(yes).
0.05::xray(yes); 0.95::xray(no) :- either(no).
0.9::dysp(yes); 0.1::dysp(no) :- bronc(yes), either(yes).
0.8::dysp(yes); 0.2::dysp(no) :- bronc(yes), either(no).
0.7::dysp(yes); 0.3::dysp(no) :- bronc(no), either(yes).
0.1::dysp(yes); 0.9::dysp(no) :- bronc(no), either(no).
evidence(xray(yes)).
evidence(dysp(no)).
query(asia(yes)).
query(asia(no)).
query(tub(yes)).
query(tub(no)).
query(smoke(yes)).
query(smoke(no)).
query(lung(yes)).
query(lung(no)).
query(bronc(yes)).
query(bronc(no)).
query(either(yes)).
query(either(no)).

The patient has a positive x-ray and no dyspnoea, and the queries ask for both values of six of the variables:

$ tddlog --evidence-probability examples/bn_asia_evidence.pl
asia(yes):      0.011678
asia(no):       0.988322
tub(yes):       0.054021
tub(no):        0.945979
smoke(yes):     0.513207
smoke(no):      0.486793
lung(yes):      0.252297
lung(no):       0.747703
bronc(yes):     0.193211
bronc(no):      0.806789
either(yes):    0.303695
either(no):     0.696305
P(e):   3.961994e-2     log10 -1.402086

The positive x-ray alone would raise the probability of tuberculosis or lung cancer (either) to 0.58; the absence of dyspnoea, which either disease makes likely, brings it back to 0.30. The last line is the probability of the two observations together. tddlog reads such programs from the usual network files itself (below).

Reachability in a graph with cycles

examples/cycle_graph.pl asks how likely a path is from node 1 to each other node of a graph of seven nodes whose fourteen edges are each present with their own probability:

0.6::edge(1,2). 0.5::edge(2,3). 0.7::edge(3,1). 0.4::edge(3,4). 0.8::edge(4,5).
0.3::edge(5,3). 0.6::edge(5,6). 0.5::edge(6,4). 0.4::edge(2,6). 0.3::edge(6,1).
0.5::edge(4,7). 0.6::edge(7,2). 0.4::edge(7,5). 0.7::edge(1,5).
path(X,Y) :- edge(X,Y).
path(X,Y) :- edge(X,Z), path(Z,Y).
query(path(1,2)).
query(path(1,3)).
query(path(1,4)).
query(path(1,5)).
query(path(1,6)).
query(path(1,7)).
$ tddlog examples/cycle_graph.pl
path(1,2):      0.632256
path(1,3):      0.460356
path(1,4):      0.399624
path(1,5):      0.754432
path(1,6):      0.571699
path(1,7):      0.199812

The graph has cycles (1, 2, 3 and back to 1, among others), so a world's paths are the least fixpoint of the two rules, which a naive reading would compute by iterating them until nothing changes. tddlog grounds the rules only for the paths that start at node 1, which are all the queries need. Such a component, whose rules each read one of its own atoms positively, is reachability, and tddlog writes it without recursion by eliminating its nodes one at a time, as Floyd and Warshall's transitive closure does, before it compiles the program.

Open it in the playground.

Integers in binary

Probabilistic programming languages such as Dice and Alea.jl compile an integer into its bits, each a random choice of its own, so that a number from 0 to 7 costs three choices rather than one per value, and arithmetic becomes circuits over the bits. The same program can be written in ProbLog. examples/adder.pl adds two numbers with a ripple-carry adder:

bit(0). bit(1). bit(2).
0.7::x(0). 0.3::x(1). 0.8::x(2).
0.4::y(0). 0.6::y(1). 0.2::y(2).

% exactly one of x(I) and y(I)
half(I) :- x(I), \+ y(I).
half(I) :- y(I), \+ x(I).
% the carry into bit I + 1
carry(J) :- x(I), y(I), J is I + 1.
carry(J) :- half(I), carry(I), J is I + 1.
% bit I of the sum
sum(I) :- half(I), \+ carry(I).
sum(I) :- bit(I), \+ half(I), carry(I).
sum(3) :- carry(3).
at_least_8 :- sum(3).

evidence(sum(0), false).
query(sum(1)).
query(sum(2)).
query(at_least_8).
query(x(0)).

x(I) is bit I of x, bit 0 the least significant, so x is odd with probability 0.7, and likewise for y. The evidence says that the sum is even, and a comparison of the sum with a constant, here x + y ≥ 8, reads the sum's bits.

$ tddlog --evidence-probability examples/adder.pl
sum(1): 0.491304
sum(2): 0.496870
at_least_8:     0.505913
x(0):   0.608696
P(e):   4.600000e-1     log10 -0.337242

The sum is odd where exactly one of x and y is, with probability 0.7 × 0.6 + 0.3 × 0.4 = 0.54, so P(e) = 0.46. Both are odd with probability 0.7 × 0.4 = 0.28, so P(x odd | e) = 0.28 / 0.46 = 0.608696. The other answers sum the 64 combinations of the six bits; the test checks them against that sum and against ProbLog. scripts/dice2problog.py translates a Dice program into a program like this one (below).

Open it in the playground.

Negation through recursion

A rule may read the negation of an atom that depends on the rule's own head. Three programs show what tddlog then does.

A game

In examples/win.pl, a position of a game is won if some move leads from it to a position that is not won. Each move is present with probability 0.5:

0.5::move(1,2). 0.5::move(1,3). 0.5::move(2,3). 0.5::move(3,4).
win(X) :- move(X,Y), \+ win(Y).
query(win(1)).
query(win(2)).
query(win(3)).
$ tddlog examples/win.pl
win(1): 0.562500
win(2): 0.250000
win(3): 0.500000

The rule defines win through its own negation, which a stratified program may not do, but the moves form no cycle, so each world has one reading. Position 4 has no moves and is lost, so position 3 is won where the move from 3 to 4 is present: 0.5. Position 2 is won where the move to 3 is present and 3 is lost: 0.5 × 0.5 = 0.25. Position 1 is won through 2 with probability 0.5 × 0.75 = 0.375, through 3 with 0.5 × 0.5 = 0.25, and through both with 0.0625, so P(win(1)) = 0.375 + 0.25 − 0.0625 = 0.5625. --ground prints the program tddlog compiles, in which win(3) has become a probabilistic fact:

$ tddlog --ground examples/win.pl
0.5::move(1,2).
0.5::move(1,3).
0.5::move(2,3).
0.5::win(3).
win(1) :- move(1,2), \+win(2).
win(1) :- move(1,3), \+win(3).
win(2) :- move(2,3), \+win(3).
query(win(1)).
query(win(2)).
query(win(3)).

Gear wheels

In examples/gearwheels.pl (Bogaerts and Van den Broeck, 2015, Example 4.13), two gear wheels turn each other, so each one's turning is defined through the other's, and a button toggles each wheel from time 0 to time 1. turns1 depends on its own negation, so the program is not stratified:

0.3::button1(0).
0.6::button2(0).
turns1(0) :- turns2(0).
turns2(0) :- turns1(0).
turns1(1) :- turns2(1).
turns2(1) :- turns1(1).
turns1(1) :- turns1(0), \+button1(0).
turns2(1) :- turns2(0), \+button2(0).
turns1(1) :- \+turns1(0), button1(0).
turns2(1) :- \+turns2(0), button2(0).
query(turns1(0)).
query(turns1(1)).
query(turns2(1)).
$ tddlog examples/gearwheels.pl
turns1(0):      0.000000
turns1(1):      0.720000
turns2(1):      0.720000

At time 0 nothing starts the wheels, and the well-founded model does not let the two support each other, so neither turns. At time 1 a wheel turns where its button is pressed, and then both turn: 1 − 0.7 × 0.4 = 0.72.

Open it in the playground.

A program with no distribution

Where the well-founded model leaves an atom undefined, the program has no distribution. In examples/unsound.pl, from the same paper, a :- \+b. and b :- \+a. leave both undefined in every world, and tddlog stops with exit status 1:

$ tddlog examples/unsound.pl
compilation error: atom a is undefined in the well-founded model of some possible world (negation through a cycle); no probability

The command line

tddlog [options] program.pl prints one atom:<tab>probability line per query, in the program's order, as ProbLog does. The options:

--vtree <strategy>
The vtree, the tree over the probabilistic facts that shapes the diagrams. Every strategy that answers a program gives the same answers; they differ in how fast they get there, and td, families and decision fail on some programs, with a message that says why. auto, the default, runs trials of the others (td, closed, families, dynamic, program, decision) over rewrites of the program, under bounds on size and work that double until one finishes. tddlog --help describes each.
--evidence-probability
After the queries, print P(e): P(e):<tab>p<tab>log10 l, p in scientific notation and l its base-10 logarithm.
--no-queries
With --evidence-probability, print P(e) alone, as for a partition function; what no observation depends on is then not compiled.
--precision <n>
Digits after the decimal point, 6 by default. A probability under 10−4 that is not zero is written in scientific notation, as ProbLog writes it.
--ground
Print the relevant ground program, as ProbLog, and exit. ProbLog reads the output, so the grounding can be checked on its own.
--stats
Print what tddlog did to stderr: the size of the ground program, the trials of auto, the largest diagrams and the time of each stage.

The exit status is 0 with answers, also where the evidence is inconsistent, 1 for a program tddlog cannot answer, with the reason on stderr, and 2 for options it does not accept, which it checks before it reads the program: an unknown option, one given twice, or one that the others leave unused.

Networks, Dice programs and LPADs

tddlog reads network files itself, and two Python 3 scripts in the repository's scripts/ write Dice programs and LPADs as programs it reads.

Bayesian and Markov networks

tddlog reads a discrete network file as a ground program, as in the asia example: a Bayesian network in BIF (.bif), Hugin (.net, .hugin), GeNIe (.xdsl) or the UAI format (.uai), and a Markov network in the UAI format, each factor an observed atom. The file's extension names its format.

tddlog examples/asia.net --query leaves
tddlog tests/regress/markov.uai --evidence tests/regress/markov.uai.evid --evidence-probability
tddlog --program examples/asia.net > asia.pl

The program queries every value of every unobserved variable (--query leaves those of the variables without children, --query a,b those of the variables named), and its answers are the network's marginals given the evidence, an Ace .inst file or, for a UAI network, a UAI .evid file (--evidence). For a Markov network, --evidence-probability prints the partition function given the evidence on a Z: line in place of P(e):, and with --no-queries that line alone, the UAI PR task. --rescale divides every row by its sum, for a file that writes its tables in percent. --program prints the program; scripts/gen_bn.py writes the same program for other systems, and its docstring has the encoding.

Dice programs

python3 scripts/dice2problog.py program.dice > program.pl translates a Dice program into ProbLog: an integer of w bits becomes w atoms, each flip a probabilistic fact, and the integer operations rules over the bits, as in the adder above. data/dice on the baselines branch holds the Dice paper's programs.

LPADs

tddlog reads a logic program with annotated disjunctions (an LPAD) written for cplint or PITA: a file that holds :- begin_lpad. (or :- begin_plp.) is read as the ProbLog program that --program prints.

tddlog tests/lpad/coin.cplint.pl
tddlog --program tests/lpad/coin.cplint.pl > coin.pl

The LPAD is the clauses between :- begin_lpad. and :- end_lpad.: h1:p1 ; h2:p2 :- body. is read as p1::h1; p2::h2 :- body. and a:p. as p::a., a head without a probability taking what the others leave. The clauses outside the markers are cplint's database clauses, which the LPAD calls through db(Goal) or the goal of a built-in such as findall/3: those it calls are kept, and db(Goal) is read as Goal; the rest, such as a program that plots the LPAD's answers, is left out, with the directives. Each query ?- prob(Q, P). in the file becomes query(Q)., and ?- prob(Q, E, P). becomes query(Q). and an evidence(L). for each literal L of the conjunction E. A program has one set of evidence, that of the file's first query: a query asked under other evidence, or under an intervention do(L), which ProbLog does not read, is named in a comment and on standard error, and left out. A clause that uses what tddlog does not read stops tddlog with its message.

From Rust, Python and C

Each binding takes the program's text and the command line's options and returns the answers in the order of the program's queries, each written as ProbLog prints it.

Rust

The crate builds from its repository, with a C++ compiler as above; in Cargo.toml:

[dependencies]
tddlog = { git = "https://github.com/Tractables/tddlog" }

tddlog::solve takes the program, Options and a function that receives what --stats would print:

let program = "
    0.1::burglary.
    0.2::earthquake.
    0.7::hears_alarm(john).
    alarm :- burglary.
    alarm :- earthquake.
    calls(X) :- alarm, hears_alarm(X).
    evidence(calls(john), true).
    query(burglary).
";
let options = tddlog::Options { evidence_probability: true, ..tddlog::Options::default() };
let solution = tddlog::solve(program, &options, &mut |_| {})?;
// `answers` is `None` where the evidence is inconsistent.
for answer in solution.answers.as_deref().unwrap_or_default() {
    println!("{answer}: {}", answer.probability);
}

The API documentation runs this example as a test, and describes Options and Solution.

Python

import tddlog

solution = tddlog.solve(open("examples/alarm.pl").read(), evidence_probability=True)
for query, probability in solution.answers.items():
    print(f"{query}: {probability:.6f}")
print(f"P(e) = {solution.evidence_probability:.6f}")

The package is not on PyPI yet: it builds from a checkout, with Python 3.10 or later. solve takes the options as keywords (vtree, evidence_probability, queries), and an error is an exception of its own: tddlog.ParseError, GroundingError or CompilationError. The Python page has the rest.

C

TddlogOptions options = tddlog_options_default();
options.evidence_probability = true;
TddlogSolution *solution;
if (tddlog_solve(program, &options, &solution) != TDDLOG_OK) {
    fprintf(stderr, "%s\n", tddlog_last_error_message());
    return 1;
}
for (size_t i = 0; i < tddlog_solution_num_answers(solution); i++)
    printf("%s:\t%f\n", tddlog_solution_query(solution, i),
           tddlog_solution_probability(solution, i));
tddlog_solution_free(solution);

The C library installs with CMake, as a CMake package and a pkg-config file; the C page covers building, linking and the header.

How it works

  1. tddlog parses the program and grounds it bottom up, only for the atoms the queries and the evidence depend on, and simplifies the ground program.
  2. It simplifies the program's acyclic part as a logic synthesis tool simplifies a circuit. The derived atoms outside recursion, the gates, are built into an and-inverter graph: each gate the OR of its rules' bodies, each body the AND of its literals, from two-input ANDs that are hashed as they are created, so that a gate the program writes twice is one node of the graph. A gate that computes an earlier gate's function by other structure, or its complement, or a constant, is found by simulating the graph on random assignments of its inputs and proving the candidates equal with a SAT solver, as in Mishchenko, Chatterjee, Brayton and Eén (2006). Such gates are merged into the earlier ones, with exceptions that docs/design.md lists, so that a gate is compiled once however often the program computes it: the bit-blasted circuits that Alea.jl writes compute many of their gates more than once.
  3. It chooses a vtree over the probabilistic facts. A tree decision diagram (TDD; Capelli, Choi, Mengel, Muñoz and Van den Broeck, 2026) is a canonical decision diagram shaped by a vtree, and the vtree decides its size. The default, auto, tries several vtrees and rewrites of the program under small bounds, and doubles the bounds until one of them finishes.
  4. It compiles each derived atom into a TDD by Tp-compilation (Vlasselaer et al., 2015 and 2016): the rules are applied to diagrams rather than to truth values, component by component, until the diagrams stop changing. Negation through recursion takes the well-founded fixpoint of Bogaerts and Van den Broeck (2015).
  5. It conjoins the evidence and counts each query against it: the weighted count of a diagram is the probability of the worlds it holds in.

The TDDs are those of the tididi library. docs/design.md describes each stage and the decisions behind it, and the results page compares tddlog with the other exact systems on their benchmarks.

Terms

The playground's account of a run and the results page use these words.

Ground program
The program without variables that tddlog compiles: the rules instantiated for the atoms the queries and the evidence depend on, then simplified. Its facts are the probabilistic facts and the choices of the annotated disjunctions, whose values make a world; its derived atoms are the ones the rules define. --ground prints it.
Component
A strongly connected component of the derived atoms: atoms that depend on each other through the rules. tddlog compiles the components in the order of their dependencies. A cyclic component, recursion as in the reachability example, is iterated until its formulas stop changing.
TDD
A tree decision diagram, the representation tddlog compiles into: a canonical decision diagram shaped by a vtree, so that a function has one TDD on a given vtree.
Vtree
A binary tree whose leaves are the diagrams' variables: the ground program's facts, and copies of derived atoms where a layout reads them through variables of their own. Every diagram of a run is built on the same vtree, and the vtree decides the diagrams' sizes: one function can take a few pairs on one vtree and millions on another.
Pairs
The size of a TDD. A node of a TDD sits at a node of the vtree and is a list of pairs, each a child on the vtree node's left and one on its right; a diagram's size is the number of its pairs, as a BDD's is the number of its nodes. The playground's "pairs at most" is the largest diagram a run built.
Formula
The TDD of a derived atom: it holds in exactly the worlds in which the atom does. The evidence is the conjunction of the observations' formulas, and each query is counted against it.
Layout
A way to build the vtree, with the rewrite of the program that it compiles: one of the strategies of --vtree other than auto. The layout a run names is the one that answered.
Trial
A layout that auto runs under bounds on the size of the diagrams, in pairs, and on the work of the operations that build them. auto runs its trials in turns and doubles the bounds each turn, and the first trial to finish answers. A run's compilations are the ones it started, those stopped at a bound included, and the time of the trials given up is the time of the compilations that did not answer. The bounds are counts, never seconds, so a run takes the same decisions on every machine.
Part
Where the part of the program that some of the queries depend on is much smaller than the whole, tddlog answers the queries in groups, each on its own part of the program, with a layout and a vtree of its own.
P(e)
The probability of the evidence: the weighted count of the evidence formula, the sum of the probabilities of the worlds in which every observation holds. Its base-10 logarithm stays exact where P(e) is smaller than the least floating-point number.
